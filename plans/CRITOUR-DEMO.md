# CritOur — 60-second demo and release gates

## What to prove

A small contribution can cause a real improvement, with the author, review and change still connected. The demo proves a stored workflow; it must not claim that CritOur automatically edits another application or verifies a remote code change.

## Prepare before recording

Use two independent consenting accounts. On the released origin, A signs in with Google and B with GitHub. Both actual provider flows must first pass live validation; the local mocked tests do not replace this step.

Choose a real project and screenshot that A owns, with a three-to-five-minute beginner task. Publish its Build Card explicitly. Prepare the development environment so the requested small improvement can actually be made. If using demonstration fixtures, label the project and narration “Demo / test data” throughout; do not call them real users or real traction.

## A concise walkthrough

| Time | Action | Evidence on screen |
| --- | --- | --- |
| 0–10 s | Open the public landing/Explore and the Build Card while signed out | Clear value, public project, concrete task, skills and estimated time |
| 10–20 s | Choose “Help this project” | Test/Idea/Design/Code, no team join required |
| 20–35 s | B writes an observation and signs in when needed | Draft restored, stored submission, Submitted state |
| 35–50 s | Switch to A; review/adopt, then record the genuinely made improvement | Owner permission, improvement explanation, approval history and Before/Feedback/After |
| 50–60 s | Show B’s portfolio and the owner-confirmed public Impact Card | Approved impact, privacy-aware credit, Copy Link / Share |

If the improvement cannot honestly be implemented during this time, say it was made between the submission and this review. Never pretend a pre-recorded result happened live. A short demo can use preauthenticated accounts after showing how the real OAuth sign-in works; label any edits in the recording.

A’s project and review history link to the result. B’s portfolio attributes the accepted contribution. Neither membership nor an unreviewed submission is an achievement. Share only owner-confirmed public content; contributor aliases require the contributor’s own setting.

## Submission gates

- Complete the live Google-A/GitHub-B flow on the actual HTTPS release, with separate browsers.
- Complete and approve the Node/Deploy Now storage adapter; a Worker build alone does not satisfy the hosting requirement.
- Back up and verify persistence and restore, then approve the production migration/deployment explicitly.
- Show one actual improvement and linked owner review, not only local fixtures or invented usage metrics.
- Check mobile, keyboard, public revocation, report/block, retries and a real social preview.
- Review the official rules again before the owner submits the form. Submission, legal consent and public deployment have not been performed.

The official page, checked 2026-11-07, specifies 2026-12-08 23:59 and a Deploy Now URL submitted via its application form. The proposed early-December submission schedule is a planning suggestion, not an automation or an entry.
